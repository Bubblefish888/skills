```markdown
# 职业作家的核心不是灵感而是流程

## 一句话总结
职业写作靠的是每天固定时间的流程化工作，而不是等待灵感降临。

## 三个关键点
1. **灵感不是核心驱动力** — 灵感只负责「收集素材」这一步的一小部分，后续的草稿、修改、定稿不需要灵感
2. **流程分解是关键** — 把写作拆成「收集素材→打草稿→冷处理→修改→定稿」五个独立步骤，每步做什么清清楚楚
3. **writer's block 的本质** — 不是没灵感，而是你在用灵感驱动创作。切换到流程驱动，就不存在「卡住」

## 原文精华摘录
> 所谓的 writer's block，本质上是你在用灵感驱动创作，而不是用流程。

## 我的思考
这个逻辑其实不限于写作。程序员写代码、设计师做方案、产品经理写文档——「流程化」这件事可能是所有创造性工作的通用解。区别在于写作的流程比较成熟（五步法），其他领域的流程还需要自己摸索。

## 行动启发
- [ ] 把我的写作流程也拆成固定步骤，每天固定时间执行，不依赖「想不想写」
```

```markdown
# 修改最近一次 commit message 的正确姿势

## 一句话总结
未 push 的 commit 用 `amend` 改 message；已 push 的 commit 用 `revert` 补偿。

## 三个关键点
1. **未 push → amend**：`git commit --amend -m "新message"`，安全无副作用
2. **已 push → revert**：`git revert HEAD` 创建一个新的反向 commit，不破坏历史
3. **核心原则**：不要改写公共历史，只改写自己本地的

## 原文精华摘录
> 不推荐对已经 push 的 commit 用 amend，会搞乱别人的历史。

## 我的思考
这个原则适用于所有分布式协作工具——只要别人可能依赖了你的输出，就别改历史，只能追加修正。
```

```markdown
# MVP 验证胜过闭门造车——一个真实的教训

## 一句话总结
花三个月闭门造车做出来的功能没人用，花两周用 Demo 快速验证迭代反而做出了用户要的东西。

## 三个关键点
1. **假设不等于用户需求** — 团队「以为」用户需要的 ≠ 用户「实际」需要的，中间隔着真实使用场景
2. **Demo 验证的效率** — 一周做一个可交互的简陋 Demo，让用户真实上手试用，比任何需求文档和设计稿都管用
3. **快速迭代的价值** — 两周内迭代四个版本，每个版本都是基于真实反馈改进，最终精准命中

## 原文精华摘录
> 我们发现我们以为用户需要的功能和用户实际想要的根本是两回事。

## 我的思考
这个教训几乎是每个产品团队的必修课。关键是：知道了这个原则后，在实际项目中能不能真正做到？很多时候迫于时间压力还是会回到「先做完再说」的老路。需要建立机制——比如强制要求每个功能上线前至少给 3 个真实用户试用过。

## 行动启发
- [ ] 下一个新功能启动时，把「第一周出 Demo → 第二周给用户试 → 第三周根据反馈迭代」写进计划里
```
